# 审阅只关心三件事：方案能否达成目标；风险点（复杂计算、边界情况、成本高的环节、大规模数据处理）是否经得起复核；性能上内存、计算与时间的权衡是否得当。
aspects:
  - id: requirements
    name: 目标与方案
    ask: 这个方案能否达成它的目标？
    criteria:
      - 目标、非目标与约束（规模、时延、预算、上线时间）写清楚，并且有具体的数
      - 方案的每个部分都能对应到目标；方案达成目标的路径说得通
      - 与更简单的做法比较过：如果更简单的做法也能达成目标，复杂的方案需要理由
    expert_questions:
      - 目标是什么，做成的标准是什么数？方案按设计实现后，能否达到这个数？
      - 方案中哪一步是达成目标的关键？如果这一步做不到，还有什么退路？
      - 有没有更简单的做法同样能达成目标（不改、用现成的工具、换一种存储）？为什么不用？
      - 非目标写了吗？方案有没有在解决目标之外的问题？
    red_flags:
      - 目标只有形容词（“更快”“更稳定”），没有数
      - 方案与目标之间缺一环，靠“应该可以”连接
      - 引入新的组件或技术，理由不是目标而是“更现代”
  - id: risks
    name: 风险点
    ask: 方案中最可能出错的地方在哪里，它们经得起复核吗？
    criteria:
      - 复杂的计算与算法（并发、一致性、数值计算、增量更新）写清楚了做法，推理过一遍是对的
      - 边界情况（空输入、超大输入、重复、部分失败、超时、编码与时区）有明确的处理方式
      - 成本高的环节（调用外部服务、大量存储或传输、昂贵的计算）指出来，并估算了量级
      - 大规模数据处理（批量读写、全表扫描、内存中的大集合）说明了数据量和处理方式
      - 方案对现有系统的假设与实际相符
    expert_questions:
      - 方案中最复杂的那段计算或算法是什么？用一个小例子手算一遍，结果对吗？
      - 输入为空、超大、重复、格式不对时会怎样？处理到一半失败、重试时会怎样？
      - 哪一步最花钱（外部调用、存储、传输、计算）？量级估过吗？用户量或数据量翻十倍时呢？
      - 有没有一次读入全部数据、或在内存中持有大集合的地方？数据量是多少？
      - 方案依赖现有系统的哪些行为？这些行为在代码或文档里确实如此吗？
    red_flags:
      - 复杂的逻辑只有一句“按某某方式处理”，没有细节
      - 只写了正常流程，边界情况与失败没有交代
      - 成本或数据量没有估算，只有“应该不大”
      - 对现有系统的假设没有核实
  - id: performance
    name: 性能与资源
    ask: 方案在内存、计算与时间之间的权衡是否得当？
    criteria:
      - 内存、CPU 与耗时有估算（量级即可），并与约束比较
      - 权衡有理由：例如用内存换时间、用预计算换在线计算、用压缩换体积，说明了换来的是什么、付出的是什么
      - 数据量或负载增长时，资源用量如何变化（线性、超线性），有说明
    expert_questions:
      - 方案常驻内存多少？峰值多少？与可用的资源相比如何？
      - 最耗时的步骤是哪一步？耗时随数据量怎样增长？
      - 方案在哪里用一种资源换另一种？这个交换值得吗？有没有代价更小的换法？
      - 估算的依据是什么（实测、基准、推算）？可信吗？
    red_flags:
      - 没有任何资源估算
      - 资源用量随数据量超线性增长，而没有说明
      - 权衡只讲了收益，没有讲代价

# 技术设计

技术设计的审阅只关心三件事：方案能否达成它的目标；方案中的风险点——复杂的计算、边界情况、成本高的环节、大规模的数据处理——是否经得起复核；性能上，内存、计算与时间之间的权衡是否得当。接口的命名、文档的格式、代码风格之类不在审阅范围内，除非它们影响上面三件事。

**审阅分两层。** 概览写方案的整体：目标与方案、风险点、性能与资源，以及几个决定方案能否成立的关键问题。正文批注只指向具体的段落。

**审阅者的角色**：一位资深的工程师，在设计评审会上逐一追问：做得到吗？哪里会出错？代价是多少？阅读设计文档，必要时阅读现有系统的代码与文档以核对设计的假设；不运行代码，不做压力测试。性能与成本只看估算的方法与量级是否合理。

**复核风险点**：对每个风险点，审阅者自己推理一遍，而不只是指出它存在。复杂的计算用一个小例子手算；边界情况逐一列出并说明设计的处理是否充分；成本与数据量按设计给出的数字推算量级。推理的过程写在批注里，作者可以据此核对。

**通用要求**
- 写法按 `skills/WRITING.md`：先写事实（设计中的哪一节、哪个假设、哪个数），再写判断（这会导致什么，影响有多大）。
- 评审别人的设计时不修改原文，问题写成给作者的意见；审阅自己的设计时，AI 可以修正与原文其他部分矛盾或计算有误之处，但不替作者决定设计。
- 关于现有系统的事实，能读到代码或文档的就核对；读不到的写成待核实。
- 表述层面的问题每次最多五条。

## goals · 目标、非目标与约束 · J · 目标与方案
- **常见问题**：目标只有形容词；没有非目标，范围不断扩大；约束（规模、时延、预算、上线时间）没有具体的数。
- **依据的材料**：设计文档。
- **审阅要点**：写出目标与做成的标准，列出非目标与约束，标出没有数的地方。
- **作者的参与**：目标与约束的数值以作者为准。

## fulfillment · 方案能否达成目标 · J · 目标与方案
- **常见问题**：方案与目标之间缺一环；关键的一步能否实现没有论证；方案在解决目标之外的问题。
- **依据的材料**：设计文档。
- **审阅要点**：沿着方案的步骤推一遍，看能否到达目标；找出最关键、最没把握的那一步，以及它做不到时的退路。
- **作者的参与**：关键一步的可行性有疑问时，写进概览的关键问题。

## alternatives · 与更简单做法的比较 · J · 目标与方案
- **常见问题**：只有一个方案；没有考虑不改、用现成工具或更简单的做法；选择复杂方案的理由与目标无关。
- **依据的材料**：设计文档。
- **审阅要点**：提出至少一种更简单的做法，判断它能否达成目标；不能达成时说明差在哪里。
- **作者的参与**：取舍由作者决定。

## hard_logic · 复杂计算与算法 · J · 风险点
- **常见问题**：并发、一致性、增量更新、数值计算等复杂逻辑只有一句话；推理中有遗漏或错误。
- **依据的材料**：设计文档；相关代码（只阅读）。
- **审阅要点**：找出最复杂的计算或算法，用一个小例子手算一遍，判断结果是否正确；写出推理过程。
- **作者的参与**：推理发现错误时，写成建议或待核实。

## failure_modes · 边界情况与失败处理 · J · 风险点
- **常见问题**：只写了正常流程；空输入、超大输入、重复、部分失败、超时、编码与时区等情况没有交代；重试造成重复写入。
- **依据的材料**：设计文档。
- **审阅要点**：逐一列出可能的边界情况与失败，说明设计对每一种的处理是否充分。
- **作者的参与**：处理方式由作者决定。

## cost_upkeep · 成本高的环节 · J · 风险点
- **常见问题**：外部调用、存储、传输或计算的成本没有估算；规模变大后成本失控。
- **依据的材料**：设计文档；价格信息（如文档给出）。
- **审阅要点**：找出最花钱的环节，按设计给出的数字推算量级，并推算规模翻十倍时的情况。
- **作者的参与**：成本是否可以接受由作者判断。

## data_volume · 大规模数据处理 · J · 风险点
- **常见问题**：一次读入全部数据；在内存中持有大集合；全表扫描；批处理的数据量没有说明。
- **依据的材料**：设计文档；相关代码（只阅读）。
- **审阅要点**：找出处理大量数据的步骤，写出数据量与处理方式，判断是否会超出内存或时间的约束。
- **作者的参与**：发现超出约束时写进关键问题。

## existing_system · 对现有系统的假设 · V · 风险点
- **常见问题**：设计假设现有系统能做某事，实际做不到；对现有接口的行为理解有误。
- **依据的材料**：现有系统的代码与文档（只阅读）。
- **审阅要点**：列出设计对现有系统的假设，逐条对照代码或文档核对。
- **作者的参与**：读不到代码或文档时写成待核实。

## constraints · 内存、计算与时间的估算 · J+V · 性能与资源
- **常见问题**：没有资源估算；估算的依据不明；估算与约束没有比较。
- **依据的材料**：设计文档；文档引用的实测或基准（可以核对的）。
- **审阅要点**：写出常驻内存、峰值内存、主要步骤的耗时与 CPU 用量的量级，与约束比较；核对估算的依据。
- **作者的参与**：估算明显缺失时写成建议。

## tradeoffs · 资源之间的权衡 · J · 性能与资源
- **常见问题**：用一种资源换另一种，只讲收益不讲代价；有代价更小的换法没有考虑。
- **依据的材料**：设计文档。
- **审阅要点**：找出方案中的资源交换（内存换时间、预计算换在线计算、压缩换体积等），判断换得是否值得，是否有更好的换法。
- **作者的参与**：取舍由作者决定。

## scaling · 随规模增长的变化 · J · 性能与资源
- **常见问题**：资源用量随数据量或负载超线性增长而没有说明；只估算了当前规模。
- **依据的材料**：设计文档。
- **审阅要点**：推算数据量或负载增长时内存、耗时与成本的变化方式，指出最先成为瓶颈的地方。
- **作者的参与**：发现瓶颈时写进关键问题。
