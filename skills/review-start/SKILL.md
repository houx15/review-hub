# review-start：分类与审核计划

## 怎么调用 RH
`RH` = `uv run <engine_root>/scripts/rh.py [--workspace <工作区>] <命令> ...`
- `engine_root`：本 skill 目录解析符号链接后（`realpath`）往上两级，即 review-hub 仓库。
- `--workspace` 是全局参数，必须写在命令名**之前**。没有设置 `$REVIEW_WORKSPACE`、工作区又不在默认的 `~/review-workspace` 时必须给。
- 会话参数可以是会话文件夹路径，也可以是 session_id。

## 输入
- 要审的产出：一个或几个文本文件（`.md`、`.tex`、`.txt` 等）。`.docx`/`.pdf` 先请用户导出为文本或 markdown。
- 可选：档位、"这次特别要查什么"。

## 输出
- `sessions/<日期>-<slug>/artifact/`：产出快照（原文件不动），`sources.json`
- `plan.json`（schema：`schemas/plan.schema.json`）：先是 `draft`，确认后 `confirmed`
- `feedback.jsonl` 里一条 `plan_confirm`

## 步骤
0. **工作区存在吗**：`<工作区>/config.yaml` 不存在时，先按 `review-setup` 初始化，再继续。
1. **建会话**：`RH new-session --slug <2–4 个英文词> <产出文件...>`。
2. **读产出，判断情境**：对照 `<工作区>/types/*/TYPE.md`（情境库：每个类型的 `aspects` 是这种情境下的审核方面）。选最接近的类型，给一句理由；混合产出列多个类型，主类型在前（混合时在第 5 步手工把另一类型的环节加进 `stages`，标 `from_type`）。没有合适的类型时，选最接近的一个作起点，第 5 步按这份产出改造审核方面。
3. **定档位**：用户指定的优先。否则：
   | 档位 | 什么时候 |
   | --- | --- |
   | `light` | 内部笔记、早期草稿、只想快速查数字 |
   | `standard` | 给导师、合作者、组会看的报告或方案（默认） |
   | `deep` | 投稿、对外发布、难以撤回的决定 |
4. **生成草稿**：`RH init-plan <会话> --type <类型> --tier <档位>`。脚本按 `TYPE.md` 和档位填好环节、预算、产出信息，留下 `TODO` 占位。
5. **补全草稿**（直接编辑 `plan.json`）：
   - `artifact.title`、`classification.rationale`。
   - **为这份产出设计审核方面** `aspects`：草稿从类型复制了默认的方面，把它们落到这份产出上：
     - 每个方面写 `covers`：这份产出里哪些部分归它看（章节、图表、附录），用产出自己的标题；
     - 每个方面写 `criteria`：2–4 条关键标准，说"好的产出在这里做到了什么"，针对这份产出具体写（例如"标题回答的是数据真正回答的问题"，而不是"问题清楚"）；
     - 每个方面的 `expert_questions`（资深审稿人会问的问题）和 `red_flags`（常见毛病）从类型复制而来，把它们落到这份产出上：删掉不相关的，补上这份产出特有的（例如这份报告用了强制二选一，就加一问"二选一的形式本身会不会放大差异"）。审核者靠它们做判断，写得越具体，审得越像行家；
     - 类型的方面不贴合这份产出时可以改名、合并、删掉或新增。新增的检查项写成自定义环节：`custom: true`、`aspect`、`criteria`（失败的样子和查什么），`id` 用英文小写；
     - 其他类型的 `aspects` 是参考例子：遇到情境库没有的产出（比如一份教学大纲），参照它们的粒度和写法设计。
   - **参考材料** `ground_truth`：在产出所在项目里找审核时要读的东西：设计文档、研究计划、代码、已保存的结果文件、文献、实验材料。只读，只记位置（绝对路径）。审核**不运行代码、不读入原始数据或日志**，所以原始日志、大数据文件不用列，除非要从里面读个别样例。产出提到但找不到的记 `available: false`，`description` 写清楚缺的是什么（这时可以不写 `location`）。
   - **每个纳入的环节**：写 `ai_checks`（查什么、怎么判断、对照哪些 `G`）。"怎么判断"写成专家的做法（读什么、比较什么、问什么），不写"重跑""重算"。
     - V 类环节（能对照已保存的结果或原文核对的）没有任何可用材料时，改为 `included: false`，在 `excluded_reason` 和 `not_checked` 写明原因。
     - J、J+V 类环节缺真值时仍然纳入（判断不依赖真值），把缺的部分写进 `not_checked`。
   - **人在环节层面的介入** `human`：这是计划阶段的预期，告诉用户大概会被问什么；具体问题到 `review-run` 拆出决策点后才确定。规则：
     - 能从真值查到的 → `none`；
     - AI 核对过、请用户抽查一下的数字 → `confirm`；
     - 材料不在项目里、只能由用户确认的前提 → `confirm`（review-run 会把它写成没有来源的主张，请用户一键确认）；
     - 有几个可列举的选项 → `choose`；
     - 只有用户知道答案、且承重 → `answer`；
     - 不承重 → `none`。
   - **用户与作品的关系** `user_role`：作品是用户自己的（或 AI 替用户写的初稿），填 `author`；用户在评判别人已经完成的作品（审稿、评审、决定是否采用），填 `evaluator`。拿不准时问一句。评判别人的作品时，AI 不改写原文，作品中需要作者决定的地方写成向作者提的问题。
   - **作者想表达什么** `intent`：类型的 `TYPE.md` 有 `ask_intent: true` 时（创意写作等），审阅之前请作者用一两句话说出这篇想表达的是什么，写入 `intent`（`source: author`）。作者不在时，从文本推断并写 `source: inferred`，在计划中请用户确认。审阅据此判断作品是否表达了作者的意图。
   - **修改的范围** `revision_policy`：`init-plan` 按类型给出默认值。以作者本人口吻写的文本（申请文书、个人陈述、随笔、小说、第一人称的路演材料）用 `narrow`：AI 只删减、收窄说法、按材料更正，不替作者新增论断；创意写作用 `none`：AI 不修改作品，只提问与建议。其余用 `full`。
   - **不适用的层次**：作品的体裁本身不要求的层次（例如申请表并不要求写成功指标），把相应检查项设为 `included: false` 并写明理由，不要让审阅者按不适用的标准评判。
   - `direction_check.question`：用一句话说出这份产出要回答的问题，问用户方向是否确定。它不属于任何环节。
   - 用户说了"特别要查什么"就写进 `focus`。
   - `RH validate <会话>` 必须通过（`TODO` 没填完会报错）。
6. **请用户确认**，用一屏以内的中文展示：
   - 类型和理由、档位；
   - 检查表：按审核方面分组，每个方面写它要回答的问题、看哪些部分、关键标准、两三个最要紧的专家问题，下面列检查项 · 能核实还是靠判断 · AI 查什么 · 你可能要做什么；改造过的方面说明为什么改；
   - 说一句：AI 只读不算，不运行代码、不重算结果，关键数字只抽查几处；
   - 说明你与作品的关系（自己的作品，还是评判别人的作品）以及 AI 修改的范围；
   - 用白话。不写 V/J、承重、决策点这类内部说法，说"可核实""需要判断""可能请你选择或给出看法"；
   - 真值来源，以及找不到的；
   - 不查什么；
   - 预计你要花几分钟（`init-plan` 按档位给默认值；产出很长、判断题多时上调，并说一句理由）；
   - 说明接下来的流程：AI 自审，在副本上自己改，再审，最多 3 轮；然后把剩下的问题和全部改动交给你，原文件在你同意之前不会动；
   - 最后单独问方向那一句。
   用户可以改档位、增删环节、补充 `focus`。改档位就用 `RH init-plan ... --force` 重新生成草稿，再补全。
7. **确认后**：
   - 用户有修改：写回，`revision` 加一；没有修改：`revision` 不变。
   - 设 `status: confirmed`、`confirmed_at`、`classification.confirmed_by_human: true`、`direction_check.answer`。
   - `RH add-feedback <会话> --kind plan_confirm`（用户说了什么就放进 `--note`）。
   - `RH validate <会话>`，然后告诉用户可以运行 `review-run`。

## 规则
- 计划确认前不开始任何审核。
- 用户对方向不确定时，建议先停下来，不审细节。
- 写进文件的说明文字用中文。
