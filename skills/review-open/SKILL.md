# review-open：启动审核界面

## 怎么调用
- `RH` = `uv run <engine_root>/scripts/rh.py [--workspace <工作区>] <命令> ...`
- `RH_UI` = `uv run <engine_root>/scripts/rh_ui.py [--workspace <工作区>] [<会话>] [--port 8765]`
- `engine_root`：本 skill 目录解析符号链接后（`realpath`）往上两级，即 review-hub 仓库。`--workspace` 写在其他参数之前；没设置 `$REVIEW_WORKSPACE`、工作区又不在默认的 `~/review-workspace` 时必须给。

## 输入
- 会话（文件夹路径或 session_id）。不给也可以：界面首页列出工作区里所有会话。

## 输出
- 一个只监听本机（`127.0.0.1`）的网页地址。
- 用户在界面上的每个操作追加为 `feedback.jsonl` 的一条记录（`source: ui`），与对话里写的反馈格式相同。
- `metrics.json` 的 `human.minutes`（`measured_by: ui_timer`）和 `by_stage_minutes`：页面可见、且用户两分钟内有操作时才计时。

## 步骤
1. `RH validate <会话>`。不通过就不启动，告诉用户哪里有问题（通常要回到 review-run 修）。
2. 看界面是不是已经开着：`curl -s http://127.0.0.1:8765/api/sessions`。返回的 `workspace` 和当前工作区相同，就直接用这个地址，不再启动。
3. 否则**在后台**启动服务（Claude Code 里用 `run_in_background`），不要在前台等它：
   `RH_UI <会话>`
   输出的第一行是地址，形如 `审核界面：http://127.0.0.1:8765/#/s/<session_id>`。端口被占用时脚本会自动换下一个，以输出为准。
4. macOS 上用 `open <地址>` 打开浏览器，然后用两三句话告诉用户：
   - 地址；
   - 页面怎么读：值得关注的段落已高亮，问题写在段落上方；没有必须完成的步骤，看到哪里、回应什么都由用户决定；
   - 页面上的操作会直接记下来，处理完回到对话说一声就行。
   - 概览下方有"答辩模式"：AI 扮演这类作品最严格的提问者，一次问一个问题；想试的话在页面上点"开始答辩"，或在对话里说一声。
5. **接住页面上的讨论**：用户在页面上发的消息只写进 `threads.jsonl`，要靠你回复。启动界面后，在后台运行 `RH inbox <会话> --wait 1800`（Claude Code 里用 `run_in_background`）。它在有新消息时退出并打印消息；超时没有消息时退出码 2。每次退出后：
   - 逐条回复：`RH reply <会话> --to M0003 --text "..."`。回答要具体，引用证据（文件和行、输出）；不知道就说不知道，并说怎么能查到。
   - 用户要求改产出：直接改副本 `artifact/`，每处用 `RH add-change` 记录（JSON 里带 `message_ids: ["M0003"]`），回复时加 `--changes R005`。原文件不动。
   - 消息以"[完成审阅]"开头：用户在页面上完成了审阅。回复一句"收到，接下来在对话中继续"，然后在对话中：定稿且有未写回的修改时，按 `review-apply` 的"写回"一步请用户确认；选择再审一轮时运行 `review-apply`。之后按 `review-learn` 回顾这次审阅，作为最后一步。
   - 消息以"[答辩模式]"开头：用户在页面上点了"开始答辩"。先回复一句"答辩在对话中进行，请回到对话"，然后在对话中按 `review-devil` 开始。
   - 用户的话其实是对审核本身的建议（"以后都要先查……"）：回复里问一句要不要记成建议；同意就 `RH add-feedback <会话> --kind suggestion --text "..." --scope this_type`。
   - 然后再次在后台运行 `RH inbox <会话> --wait 1800`。用户说不用了或会话结束时停止。
6. 用户回来后：`RH status <会话>` 看还剩什么。
   - 用户在界面上签收了"再来一轮"、接受了要改的发现、改选了决策点，或撤销了 AI 的改动 → 运行 `review-apply`。
   - 签收"交付"、有还没写回的 AI 改动 → 按 `review-apply` 的"写回"一步，给用户看全部差异，同意后写回。
   - 签收"交付"、没有改动 → 审核结束。
7. 服务可以一直开着（它只读写文件，自审写入新结果后页面会自动刷新）。用户说不用了，或会话结束时，停掉后台任务。

## 界面上有什么
- **左栏 · 审核地图**：上游到下游的检查项（类型有 `aspects` 时按方面分组，如科研报告的七个方面），每项下列出决策点和主张核对情况；点环节只突出这个环节，点决策点跳到原文。
- **中栏 · 产出**：原文上叠审核层。发现按严重度着色；主张后面的小标记表示 ✓ 已核对、! 有发现、? 未查；决策块嵌在陈述这个选择的段落下面；右侧细条标出所有待处理的位置。
- **AI 的改动**：自审时 AI 在副本上改过的地方用绿色下划线标出，点开看改前改后，可以保留或撤销；顶部可以切换"AI 修改后 / 原版"。
- **右栏**：「审阅意见」（研究决策 → 值得追问之处 → 具体问题 → 缺少出处的论断 → AI 的修改 → 表述问题 → 已处理）、「讨论」（整份产出的讨论、各条目上的讨论、给审核的建议）、「完成审阅」、「核查记录」（`certificate.md`）。每张卡片下面都可以和 AI 讨论。

## 规则
- 界面不调用模型、不联网，只读会话文件、追加 `feedback.jsonl` 和 `threads.jsonl`（用户的消息）、更新 `metrics.json` 的用时。AI 的回复由你用 `RH reply` 写。
- 界面不能确认计划（那一步在 review-start 的对话里做），也不能修改产出。
- 页面不设任何关卡：没有必须先回答的问题，有未处理的重大问题也可以完成审阅（会一并记下）。
- 不要把服务改成监听 `127.0.0.1` 以外的地址。
