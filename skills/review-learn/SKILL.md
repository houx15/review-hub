# review-learn：从用户的回应中改进审阅

每一次审阅，用户的回应都是对审阅本身的评价。这个技能把这些评价变成对审阅框架的具体修改，并记录每次修改的来由，使审阅随使用逐渐变好。

## 什么时候运行

这是每次审阅的最后一步，由 AI 主动进行，并告诉用户正在做什么：
- 用户在页面上点了"定稿"或"再审一轮"（对话中收到以"[完成审阅]"开头的消息），或在对话中表示这次审阅结束；
- 写回原文件之后（`review-apply` 的最后一步）。

开场用一句话说明：接下来回顾这次审阅，看哪些地方可以让今后的同类审阅做得更好，大约需要几分钟，可以随时跳过。此时用 `RH signals --session <会话>` 只看这一次审阅。

几次审阅之后（或用户要求时），用 `RH signals` 汇总全部审阅，寻找跨审阅的模式。

**用户在这次审阅中回应很少时**，不要凭空提议，先问两个简短的问题，并把回答记下（遗漏的问题记为 `RH add-feedback <会话> --kind missed --text "..."`，其余记为 `--kind suggestion`）：
1. 这次审阅中，哪些意见最有用，哪些是多余的？
2. 有没有你注意到、但审阅没有提出的问题？

## 怎么调用 RH
`RH` = `uv run <engine_root>/scripts/rh.py [--workspace <工作区>] <命令> ...`（`engine_root`：本技能目录解析符号链接后往上两级）。

## 依据：用户的回应意味着什么

| 用户的回应 | 对审阅的含义 |
| --- | --- |
| 批注被标为"不成立" | 误报。看它属于哪个检查、为什么不成立，考虑收紧这一检查或补充排除条件 |
| 批注被标为"无关紧要" | 价值低。考虑降低这类问题的级别，或改为只在表述问题中列出 |
| 批注被标为"同意"或"同类问题" | 有价值。同类问题出现两次以上的，考虑写成规则，以后主动检查 |
| AI 的修改被撤销 | 修改过度或方向错误。看撤销时的备注，调整修改的尺度 |
| "AI 遗漏的问题" | 最重要的信号。补充相应层面的专家问题或常见问题，使下一次能发现它 |
| 对"值得追问"的回应 | 用户认为哪些疑问值得、哪些不值得，用来调整线索的选择 |
| "对审阅的建议" | 用户直接写下的要求，按其适用范围（本次、同类文本、所有审阅）处理 |
| 与 AI 讨论某条批注 | 这条批注可能不清楚，或用户不同意；读讨论内容判断是写法问题还是判断问题 |
| 批注从未被打开 | 可能是噪声，或位置与分量安排不当；结合它的严重程度判断 |
| 打开后看了很久却没有回应 | 可能写得不清楚，或用户拿不准；考虑改进写法或补充依据 |

这些都来自用户在页面上的正常使用（点击、回应、讨论），不需要用户另外做任何事。阅读记录（`activity.jsonl`）只保存在本地的审阅文件夹中，只用于改进审阅。

## 步骤

1. **汇总回应**：`RH signals --session <会话>`（这一次）或 `RH signals`（全部）。它读取已完成的审阅，按文本类型汇总上表中的各项，写入 `ledger/signals.json`，并打印每类文本的概况（同意、不成立、无关紧要的比例，撤销的修改，遗漏的问题）。
2. **读具体内容**：打开 `ledger/signals.json`，逐条读不成立与无关紧要的批注（连同用户的备注）、被撤销的修改、遗漏的问题、建议和对线索的回应。只看数字不够，模式在具体内容里。
3. **提出修改**：对每个值得改进的模式，写一条提议。每条包括：
   - **修改什么**：具体到文件与位置，以及修改后的原文。可以修改的地方：
     - `<工作区>/types/<类型>/TYPE.md` 中某一层的 `expert_questions`、`red_flags` 或 `criteria`，或某个检查的说明；
     - `<工作区>/types/<类型>/rules.md`：这类文本的审阅规则，例如"必须检查……""不要报告……"；
     - `<engine_root>/skills/WRITING.md`：补充一组写法对比（用户认为难懂、或自己改写过的批注）；
     - `<工作区>/personal/preferences.md`：适用于所有审阅的偏好；
     - `<工作区>/personal/blind-spots.md`：用户自己的作品中反复出现的问题，以后审阅时优先检查。
   - **为什么**：引用具体的回应（审阅名称与编号），说明它们共同说明了什么。
   - **预期的效果**：下一次审阅会因此多发现什么、少报告什么。
   一次只提最有把握的几条（通常不超过五条）。只出现一次的回应，除非是用户明确的建议或遗漏的重要问题，暂不据此修改。
4. **写出提议**：写入 `<工作区>/ledger/proposals/<日期>.md`，按上面的格式，用 `skills/WRITING.md` 的写法。
5. **逐条请用户决定**：在对话中逐条展示（修改后的原文与理由），请用户同意、修改或拒绝。
6. **写入同意的修改**：按用户最终同意的文字修改对应文件；`TYPE.md` 修改后运行一次 `RH validate`（任选一个该类型的审阅）确认格式无误。
7. **记录**：每条提议的结果（同意、修改后同意、拒绝）追加到 `<工作区>/ledger/learning-log.jsonl`，每行 `{"date", "type", "target", "change", "why", "decision", "signals"}`。被拒绝的提议同样记录，以免以后重复提出。

## 规则
- 修改只写入用户同意的内容。
- 区分正确性与偏好：正确性的规则（例如"必须检查空档条件与对照在格式上是否一致"）写进类型的规则；用户的个人偏好写进 `personal/preferences.md`。
- 不为了提高"同意"的比例而删减检查：误报要通过收紧检查的条件来减少，而不是取消检查。
- 修改框架时保持原有的层次结构与写法；新增的专家问题要像审稿人会问的问题，而不是任务。

## 怎样看审阅是否在变好
`RH signals` 的概况可以按时间比较：同一类文本中，"不成立"与"无关紧要"的比例应当下降，"AI 遗漏的问题"应当减少，用户花的时间应当减少，而同意的比例应当保持或上升。
