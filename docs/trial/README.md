# 试跑记录：合成产出上的端到端测试（2026-10-22 夜）

这次试跑**不满足** Phase 1 的完成标准：完成标准要求用你的真实产出，并由你判断发现是否有价值。这里只是在一份我自己造的、埋了错的报告上，按 skill 文本手动走完整个流程，用来找出格式和流程上的缺口。

## 被审的东西

`tests/fixtures/salary-audit/`：一个虚构的简历审计项目（数据生成、起薪解析、配对分析、报告）。报告由"AI"写成，里面埋了 6 个错误，答案在 `tests/answer-keys/salary-audit.md`。审核时答案文件移出了仓库，审核者看不到。原项目复制到临时目录后再审，仓库里的 fixture 没有被改动。

## 试跑暴露的问题，以及已经做的修改

| 问题 | 修改 |
| --- | --- |
| 两个查找者在证据里写了示意性、并未真正运行的命令；验证者发现并换成真实重跑 | skill 文本明确禁止；`RH add-finding` 机械核对锚点和文件摘录，不符就拒绝写入 |
| 三个查找者大量重复，严重度和环节标得不一致 | 验证者负责去重、统一严重度和环节，标出根源 |
| 一个解析错误引出三条发现，读起来像三个问题 | 新字段 `caused_by`，摘要把连带问题折叠在根源下 |
| 预测问题放在结果后面，等于没问 | 摘要里预测放在最前 |
| 证据路径很长，难读 | 摘要中路径相对项目根目录，每条最多 2 条证据、摘录最多 6 行 |
| 第 2 轮重写 map 后，旧发现引用的主张 id 失效 | 每轮存档上一轮 map；只对当前版本检查引用 |
| 手写锚点的前后文很费事、容易错 | `RH anchor` 自动生成并检查唯一性 |
| 摘录里用 `...` 省略行被误判为编造 | 允许省略号 |

## 冷启动试跑：只给 skill 文本的新 agent

为了确认 skill 文本本身够用，而不是靠我脑子里的上下文，让一个**完全没有上下文**的 agent 只按 `SKILL.md` 跑了一遍 setup → start → run（第 1 轮），审的是原始 fixture 的新副本，答案和上面的试跑记录都临时移出了仓库。中途因用量上限中断一次，恢复后完成。

- **结果**：6 个埋的错误全部抓到，误报 0。另报了 4 条成立的发现：没记录模型版本和温度、每份简历只调用一次、只用完整配对会丢掉有性别差异的拒答、均值被极端值主导。它的 F001（"数据是合成的"）也成立：当时数据生成脚本放在 fixture 项目里，并写明了"fixture"。这是 fixture 的缺陷，已把脚本移出项目。
- **AI 工作量**：4 个审核者，有效时间约 10 分钟，`RH` 命令只失败一次（锚点不唯一，属于设计行为）。
- **摘要原样**：[summary-cold-run.md](summary-cold-run.md)。
- **它列出的 18 处 skill 文本问题和 8 处脚本问题**，已全部处理：
  - 新命令 `RH init-plan`：按 TYPE.md 和档位生成计划草稿，留 `TODO` 占位，未填完时校验不过。
  - 每个 skill 开头说明怎么找到 `rh.py`，以及 `--workspace` 必须写在命令名之前。
  - 档位怎么选写进 review-start。
  - 决策点状态和人的动作改成一张表，覆盖所有情况。
  - 区分"前提"和"决策点"：前提写成主张，由用户一键确认。
  - `source_type` 按"应当来自哪里"标，与是否已核实无关。
  - 查找者"核对过没问题"的主张也要经验证者确认，才能标 `verified`。
  - 验证者可以打开查找者的脚本重跑，但看不到查找者的推理。
  - `inherited` 可以只指向根源发现（`caused_by`），不必硬找一个决策点。
  - 代码实际做的与作者声明的选项不一致时，怎么记录。
  - `round-end` 各个计数的定义。
  - 摘要里会话内的路径也缩短，命令显示运行目录；`introduced` 的中文改为"产出本身的问题"；预测型决策点不再重复显示问题；证据文件访问不到时给出提示。

## 第二次冷启动试跑（修改 skill 文本之后）

数据生成脚本已移出项目，所以这次审核者看不到"数据是合成的"。

- **结果**：6 个埋的错误全部抓到，误报 0；9 条发现，按根源合并为 7 个问题。另报了 1 条答案里没有、但成立的发现（拒答在性别间不均）。摘要见 [summary-cold-run-2.md](summary-cold-run-2.md)。
- **AI 工作量**：4 个审核者，有效时间约 9 分钟。`RH` 失败 1 次：候选里有值为 null 的字段，现在脚本会自动去掉。
- **第一次的 18 处文本问题没有再出现。** 这次报出的是更细的问题，已经处理：
  - **预测问题泄露了答案。** 它写成"去掉拒答后你预期……"，等于先说出了主要发现。现在规定预测问题只能问对研究问题本身的预期。
  - review-start 和 review-run 对"前提"的处理不一致，已统一为一键确认。
  - V 类决策点核实出问题时，原来被归到"AI 默认"，敏感度结果因此看不到。现在改为请用户确认。
  - 查找者的输出格式里写明四种证据的完整形状和锚点命令；新增 `RH check-candidates`，在交给验证者之前先检查一遍。
  - 验证者可以改写标题和说明，避免只保留部分论点后和别的发现重叠（这次因此多算了一条 S1）。
  - `origin_decision` 只用于继承来的问题；代码错误算"产出本身的问题"。
  - 分组规则、敏感度由谁做、`--agents` 怎么数。
- **还没解决**：`docs/spec/SCHEMAS.md` 和 `schemas/examples/` 用的也是"起薪性别差异"这个情景，并且以拒答解析错误为例。skill 让 agent 读 SCHEMAS.md，所以在这个 fixture 上做冷启动测试会被提示。真实使用不受影响；以后测试最好换一个不同主题的 fixture。

## 还没解决、需要你看的

1. **合成产出太干净。** 报告只有 27 行，代码是 Python，错误是我埋的。你的真实报告更长，可能是 LaTeX/Word，代码可能是 R 或 Stata，真值可能在服务器上。这些都没测过。
2. **摘要还是偏长。** 第 1 轮 7 个问题，摘要 228 行。可能还要再压，例如 S2 默认只显示一句话和一条证据。等你看过真实产出的摘要再定。
3. **拆解（写 map.json）完全靠编排的 agent**，是整个流程里最费事的一步：3 个决策点、9 个主张，写了不少 JSON。真实报告可能有几十个主张，需要看看会不会太慢。
4. **人的用时没有测**（Phase 1 没有界面，只能自报）。
5. **只支持文本产出。** `.docx`、`.pdf` 需要先转成文本，现在没有处理。
