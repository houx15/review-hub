# Review Engine：人机协同审核系统设计

> 这是设计文档的 markdown 快照（2026-10-21）。可编辑的原文档在 claude.ai：
> https://claude.ai/artifact/EQ8rRMbeiDsJcS8uxkcaj5
> 两者不一致时，以原文档为准；开发中做出的设计决定，记录在 `docs/spec/DECISIONS.md`。

## 目标

Review Engine 是一套可接入任意 AI agent 的 skill 加一个本地审核界面。它的目的：让人更快地对 AI 在做的事建立心智模型，降低切换和审核成本，提高交付质量。

它借鉴 Claude Code 的 code review 架构，但面向没有标准答案的开放产出：产品方案、科研报告、研究计划、文章。要解决四个核心问题：

1. **AI 自审**：AI 先审自己的产出，必要时多花时间和轮次，交给人的东西已经过一轮有证据的核查。
2. **心智模型**：用什么交互和辅助，让人最快理解整体，并对关键点深入思考。
3. **高效反馈**：在 AI 提供的脚手架下，人以最低成本给出高信息量的反馈。
4. **长期沉淀**：反馈被积累下来，系统越用越省人力，同时不降低质量。

衡量标准借用 code review 博客的思路：同类任务里，人花的审核时间和需要给的反馈越来越少，而事后才发现的问题（逃逸）没有变多。

## 相关工作

单点能力都有人做过，但还没有一个系统把"AI 自审、帮人建心智模型、结构化反馈、规则沉淀"连成闭环，并且面向开放产出。

**一、AI 能审到什么程度**

| 工作 | 发现 | 对设计的启示 |
| --- | --- | --- |
| [CriticGPT](https://arxiv.org/abs/2407.00215)（OpenAI, 2024） | 模型写的批评比付费人工评审抓到更多 bug；人加模型的组合抓到的问题与模型相当，但幻觉更少 | 机器找、人裁决的分工有实证支持；用人为插入错误来训练和评估，正是埋错校准 |
| [SPOT](https://arxiv.org/abs/2505.11855)（2025） | 83 篇因勘误或撤稿出名的论文上，最好的模型召回不超过 21.1%、精确率不超过 6.1%，多次运行很少找到同一个错误 | 只给文本时 AI 审科研很弱且不稳定。必须接入真值（数据、代码、日志），并对多次运行做聚合 |
| [Google PAT](https://arxiv.org/pdf/2606.28277)（2026） | 分段的专门审核 agent 加推理扩展，在 SPOT 数学子集上召回明显提升；已在 STOC、ICML 作为投稿前工具试点 | 按环节分工的审核者是对的方向；审核放在作者一侧、交付之前 |
| [statcheck](https://r-bloggers.com/?p=142272)（Nuijten 等） | 自动重算心理学论文的 p 值，约一半论文至少一处不一致，约八分之一可能影响结论 | 机械核查收益极高，是 `checks/` 的样板；更进一步是让数字由程序生成 |

**二、怎样让人真的动脑**

| 工作 | 发现 | 对设计的启示 |
| --- | --- | --- |
| [认知强制函数](https://www.eecs.harvard.edu/~kgajos/papers/2021/bucinca2021trust.shtml)（Buçinca 等, 2021） | 先让人自己判断等设计显著减少过度依赖，但最有效的设计用户最不喜欢 | 强制只用在少数承重点上，并且可以关闭 |
| [AI 应该挑战而不是服从](https://arxiv.org/html/2411.02263v1)（Sarkar, 2024） | AI 作为"挑衅者"给出批评、反论和备选，界面应更像记号系统而不是聊天 | 决策点卡片就是一种记号；AI 的质疑以短条目挂在节点上 |
| [Scim](https://arxiv.org/abs/2205.04561)（Fok 等, 2023） | 按类别着色的高亮引导注意力，均匀分布、密度可调；没有高亮的段落会让人不安 | 文档内按环节着色的注意力层；"查过、没问题"要明确标出 |
| [EvalGen](https://people.eecs.berkeley.edu/~bjoern/papers/shankar-validators-uist2024.pdf)（Shankar 等, 2024） | "标准漂移"：人需要标准来评判输出，评判输出又在帮人定义标准 | 规则不能全部预先写好，要从你的裁决中长出来，并允许改写 |

**三、怎样表示决策**

| 工作 | 要点 | 对设计的启示 |
| --- | --- | --- |
| [QOC 设计原理](https://acawiki.org/Questions,_Options,_and_Criteria:_Elements_of_design_space_analysis)（MacLean 等, 1991） | 用问题、选项、标准记录设计空间；QOC-E 加入证据 | 决策点卡片采用 问题、选项、标准、证据 四要素 |
| [Boba](https://idl.uw.edu/papers/boba)（Liu 等, 2020） | 多重宇宙分析系统，用决策图展示分析选择，敏感决策加深颜色 | 全局地图按敏感度标承重点 |

**四、审核到底是为了什么**

[Bacchelli 与 Bird](https://2013.icse-conferences.org/content/expectations-outcomes-and-challenges-modern-code-review.html)（ICSE 2013）：找缺陷是主要动机，但实际产出更多是知识传递、团队感知和备选方案；理解是审核的核心。这支持把"帮人建立心智模型"放在和"找错"同等的位置。

## 从 Claude Code Review 再借鉴的理念

来源：[How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/)。

| 理念 | 博客里的做法 | 在 Review Engine 里的对应 |
| --- | --- | --- |
| 小改动比大审核重要 | 改动小，容易审、调试、撤回 | 按环节在产出过程中逐段审；最后只看各段之间是否一致 |
| 审核像拼写检查一样持续 | 人看之前已被 Claude 审、修过一轮 | `review-aware` 在 agent 每完成一个环节时触发一次轻量自审 |
| 出示输出，而不是宣称完成 | 给 Claude 能运行的东西，要求展示结果 | 验证清单里每条"已查"附实际运行的命令和返回结果 |
| 发现带来源标签 | Important / Nit / Pre-existing | 标明：本轮引入、来自原始材料或数据、还是继承自上游决策 |
| 每条发现都要有回应 | 修，或写理由关闭；未关闭不能合并 | 有未回应的 S1 不能签收；S2 可批量"无所谓"关闭，但必须点一下 |
| 噪声对 agent 作者代价更高 | agent 会去修每个小问题，多一轮 | `review-apply` 只修你接受的发现；表述类问题默认只列不修 |
| 优秀的 REVIEW.md 是短的 | 说清失败的样子，限制小问题数量，要求证据，摘要以数量开头 | 摘要第一句是"S1 两条、S2 三条"或"没有需要你处理的问题"；表述类每次最多五条 |
| 在已知干净的产出上测误报 | 在干净 PR 上跑审核者统计误报 | 评测集里放几份你认可的好产出，专门测误报率 |
| 三轮之后退一步 | 三轮后请作者重新考虑整体做法 | 连续三轮仍有新 S1，提示你回到上游重新考虑设计 |
| 夜间审已有代码 | 审核 agent 每晚扫描现有代码 | 可选：对长期存在的项目文档做低频扫描，检查是否与最新结果矛盾 |
| 方向问题要早提 | 早在讨论里提出，而不是阻塞写完的 PR | 计划确认阶段专门问一句"方向你确定吗" |
| 收紧护栏 | 事故率上升时自动收紧审批（他们还没做到） | 某类型逃逸率上升时，默认档位自动提高一级 |

## 设计原则

1. **决策点是基本单元。** 一份产出被拆成一张决策点图：每个关键选择、备选项、依据和下游依赖。决策点同时是审核的单位、心智模型的节点、反馈的锚和沉淀的对象。
2. **可验证的交给机器，判断题留给人。** 有真值可对照的错误由 AI 带证据核查；没有真值的判断题由 AI 摆出证据和选项，人来裁决。
3. **没有证据的发现不发。** 每条发现必须指向真值中的具体位置，否则丢弃。精确率优先于召回率。
4. **先结构，后细节。** 人先看到全局和承重点，再决定往哪里深挖。
5. **逼人做决定，不逼人读得更细。** 人的投入体现为明确的裁决和预测，而不是阅读时长。
6. **审核强度按风险分级。** 轻量、标准、深度三档。
7. **文件即接口。** 所有状态都是工作区里的普通文件，任何能读写文件的 agent 都能接入。
8. **本地优先。** 产出、反馈和度量数据都留在本地。

## 系统架构总览

三部分：任意 AI agent 上运行的一套 skill、本地工作区文件夹、本地审核界面。三者之间只通过文件交换信息。

```
 ┌────────────────────────┐        ┌──────────────── 工作区文件夹（本地）────────────────┐
 │ AI agent（任意）        │ 读取规则 │  ┌──────────────┐                                  │
 │  review-setup  初始化   │◀────────│  │ 类型与规则    │ TYPE.md · rules.md · checks/     │        ┌──────────────┐
 │  review-start  分类与计划│         │  └──────▲───────┘                                  │        │ 你            │
 │  review-run    自审流水线│         │         │ 升级规则                                  │        │ 确认计划·裁决  │
 │  review-open   启动界面  │         │  ┌──────┴───────┐                                  │        │ 签收·记录逃逸  │
 │  review-apply  按反馈修改│         │  │ 账本          │ 事故 · 回放评测集 · 规则提议       │        └──────▲───────┘
 │  review-learn  提议升级  │         │  └──────▲───────┘                                  │   注意力支持 │ 裁决与反馈
 │  review-stats  度量报表  │         │         │ 记录                                      │        ┌──────▼───────┐
 │  review-aware  生成时附来源│ 写入结果 │  ┌──────┴───────┐                                  │  展示   │ 审核界面      │
 │                        │◀───────▶│  │ 本次会话      │ plan · map · findings ·          │◀──────▶│ 地图·决策卡片 │
 │                        │ 读取反馈 │  │              │ certificate · feedback · metrics │ 写回反馈 │ 发现队列·解释器│
 └───────────▲────────────┘        │  └──────────────┘                                  │        └──────────────┘
             │ 读取 / 修改           └────────────────────────────────────────────────────┘
 ┌───────────▼────────────┐
 │ 产出：报告、方案、计划、文章│
 └────────────────────────┘
```

一次审核：agent 读取产出和规则，执行自审，把结果写进本次会话；界面展示给你，你的裁决写回会话；agent 读取反馈后修改产出。会话结束后，反馈和事故进入账本，经你批准后升级为规则，供下一次使用。

## 工作区文件夹

系统第一次运行时选定一个文件夹，之后所有长期记录都放在这里。项目本身的规则放在项目仓库的 `REVIEW.md` 里，工作区只放跨项目的东西。

```
<workspace>/
  config.yaml            # 默认档位、启用的类型、接入的 agent
  personal/
    blind-spots.md       # 个人盲点模式（跨所有类型）
    preferences.md       # 表述、格式等偏好（只影响怎么说，不影响查不查）
  types/
    research-report/
      TYPE.md            # 环节链、每个环节的失败定义、真值来源、介入点
      rules.md           # 累积的审核规则，每条带命中次数
      checks/            # 由规则升级而来的自动检查脚本
    research-plan/  product-spec/  writing/  ...
  sessions/
    <date>-<slug>/
      artifact/          # 被审产出的快照
      plan.json          # 本次审核计划
      map.json           # 决策点图
      findings.jsonl     # AI 的发现，每条带证据
      certificate.md     # 验证清单：查了什么、怎么查、没查什么
      feedback.jsonl     # 你的裁决和反馈
      metrics.json       # 用时、轮次、预测准确度等
  ledger/
    incidents.jsonl      # 事后发现的逃逸问题
    rule-proposals.jsonl # 待批准的规则升级
    eval/                # 由事故构成的回放评测集
```

规则分三层：个人层跟着人走，类型层可以分享，项目层留在项目里。一条项目规则在两个以上项目里命中，系统提议把它升到类型层。

## Skill 套件

| Skill | 什么时候用 | 产出 |
| --- | --- | --- |
| `review-setup` | 第一次使用 | 选定工作区，生成 `config.yaml` 和四个初始类型 |
| `review-start` | 有一份产出要审 | 自动分类、生成本次审核计划，等人确认 |
| `review-run` | 计划确认后 | 执行 AI 自审流水线，产出决策点图、发现和验证清单 |
| `review-open` | 自审完成后 | 启动本地审核界面 |
| `review-apply` | 人给完反馈后 | 读取反馈，修改产出，只对改动部分及其下游再审 |
| `review-learn` | 每次审核结束，或定期 | 从反馈中提出规则升级，人批准后写入规则库 |
| `review-stats` | 想看效果时 | 汇总自我实验的度量 |

可选的 `review-aware`：agent 生成产出时就加载，要求每个数字和主张附来源、每个关键选择写明备选项。

## 审核类型与自分类

每种类型是一份 `TYPE.md`：一条有依赖关系的环节链，每个环节写明失败长什么样、真值在哪、属于可验证（V）还是判断（J）。

| 类型 | 环节链（上游 → 下游） | 主要真值来源 |
| --- | --- | --- |
| 科研报告 | 文献与证据 (V) → 问题与 framing (J) → 研究设计与识别 (J+V) → 操作化定义 (J) → 测量方式 (V) → 测量是否可靠 (J) → 变量选择 (J+V) → 分析与稳健性 (V) → 数字解释 (V) → 可视化 (V) → 结论 (J+V) | 原始数据、日志、代码、stats 文件、原文献 |
| 研究计划 | 问题与贡献定位 (J) → 文献与空白 (V) → 理论与假设 (J) → 设计与识别 (J) → 操作化与测量 (J) → 数据可得性 (V) → 分析计划 (V) → 预算、时间与风险 (V) | 文献、数据文档、预算表 |
| 产品方案 | 用户与问题 (J) → 关键假设 (J) → 方案与备选 (J) → 流程与交互 (V) → 边界与失败状态 (V) → 成功指标定义 (J+V) → 可行性与成本 (V) → 上线与风险 (J) | 用户研究、行为数据、原型测试、技术文档 |
| 文章写作 | 目的与读者 (J) → 核心论点 (J) → 结构 (J) → 论据与引用 (V) → 清晰度 (V) → 语气与风格 (J) | 引用的原文、写作风格样本 |

**自分类**：`review-start` 给出类型判断和理由；人可以确认、改类型或新建类型。新类型先只有环节链，规则用几次后长出来。

**辅助调整**：一份产出可混合多种类型，审核计划合并环节链并标出合并处。环节链本身可在界面上增删、调整，写回 `TYPE.md`。

## 审核框架初始化

每次审核开始，AI 先生成审核计划，以框架图形式展示，人确认后才开始。计划回答：

- **AI 自己查什么**：每个环节对照哪些真值、用什么方法。
- **人在哪里介入**：所有 J 类，以及验证失败或无法验证的 V 类。
- **介入时做什么**：确认、在备选中选择、给出预测，还是写一句理由。
- **花多少**：档位和人预计要花的分钟数。AI 一侧只记录轮次和耗时：skill 运行在用户现有的 agent 里，不单独调用 API，token 和美元无法可靠计算。

| 档位 | 适用 | AI 做什么 | 人预计花多少时间 |
| --- | --- | --- | --- |
| 轻量 | 内部笔记、早期草稿 | 单个审核者，只查 V 类，不做敏感度分析 | 几分钟 |
| 标准 | 给导师或合作者看的报告、方案 | 每个环节并行查找 + 独立验证 + 决策点图 | 15–30 分钟 |
| 深度 | 投稿、对外发布、难以撤回的决定 | 标准档 + 独立证伪 + 敏感度或多重宇宙分析 + 埋错校准（可选） | 视产出而定 |

（时间是目标值，需要由自我实验数据校准。）

## AI 自审流水线

1. **拆解**：把产出拆成决策点图和主张清单。每个主张标注来源类型：数据算出、文献、用户说过的、模型推断。没有来源的主张单独列出。
2. **查找**：按环节并行，每个审核者只负责一段环节链，读取 `TYPE.md` 的失败定义和 `rules.md` 的规则。
3. **验证**：另一组新上下文的 agent 拿着真值逐条核查候选发现。给不出证据位置的发现直接丢弃。深度档还会让一个 agent 专门尝试推翻每个核心结论。
4. **敏感度**：对可改动重跑的分析选择，换一种做法看结论变多少。变化大的标为承重点。
5. **排序**：去重，按严重度排序：S1 改变主结论或使设计失效，S2 改变某个具体陈述，S3 只是表述。
6. **验证清单**：写明查了什么、怎么查的（附命令和结果），以及没查什么、为什么没查。

**收敛规则**：再审只针对改动部分及其下游；同一发现不重复提出；连续两轮没有新的 S1 或 S2 就停止；连续三轮仍有新 S1，提示回到上游。上游决策点一改，下游已确认的决策点自动失效。

## 审核界面：有效的脚手架

有效的脚手架承载人的思考，而不替人思考，并随人熟练逐步撤掉。关键是给每一种认知任务配上成本最低的交互形式。

### 交互形式与认知任务的匹配

| 交互 | 用在哪里 | 为什么 | 例子 |
| --- | --- | --- | --- |
| 只读 | 定向和背景 | 理解全局不需要表态 | 一句话结论、环节地图、"没查什么" |
| 确认（一键） | 已有证据的 V 类结果 | AI 已核查，人只抽查 | 数字旁的来源标记：点开看原文，确认或标错 |
| 选择（2–4 个选项） | 选项可列举或计算的 J 类决策点 | 识别比回忆便宜；选项配上敏感度 | 职业固定效应 / 职业大类固定效应 / 不加，各自结论变多少 |
| 回答（开放输入） | 承重点上只有人能给的答案 | 只有人知道自己的目标和预期；同时检验心智模型 | "你预期效应方向是什么？" |
| 质疑（可忽略） | AI 的反论和另一种视角 | 提供视角但不强迫 | "如果只看全职岗位，结论还成立吗？" |

### 什么时候提问，什么时候给选择

1. 答案能从真值查到：不问人，AI 去查，结果交给人确认。
2. 答案是有限几个合理选项之一：给选择。
3. 答案只存在于人的目标、判断或预期中，且这个点承重：提问。
4. 不承重的判断：不打扰，记为"AI 默认"，签收时统一列出。

**注意力预算**：每次审核开放问题不超过 3 个（深度档 5 个），选择不超过 10 个。超出的按承重程度排序，其余进入签收清单。

### 文档内交互

审核发生在产出本身上。产出渲染为文档，上面叠一层审核层：

- **环节着色**：每段按所属环节着色，可按环节开关，支持多遍阅读。
- **来源标记**：每个数字和主张旁有标记：已核对（悬停显示文件、行号、命令或原文片段）、有发现、未查。"查过没问题"也要显式标出。
- **内嵌决策块**：文中陈述某个选择的地方，折叠着决策块：问题、已选项、备选项、敏感度。展开即可改选。
- **预测闸门**：关键结果段落先遮住，请人写下预期，提交后揭晓并显示差距。
- **页边质疑**：AI 的挑战以页边短注出现，可转成问题或忽略。
- **修改建议**：AI 建议的改动以修订模式显示，逐条接受或拒绝。
- **滚动条小地图**：在滚动条上标出需要处理的位置。
- **地图与文档联动**：地图上点节点，文档滚到对应位置，反之亦然。

每个操作写成一条锚定的反馈记录。锚点用文本引用加决策点 id（参考 W3C Web Annotation 的文本引用方式），产出改写后反馈仍能找到原位置。

示意（文本版）：

```
┌─────────────────────────────────────────────────────┐
│▌环节：测量                                          │   ┌──────────────────────┐
│▌薪资结果取模型给出的起薪        [✓ 已核对]           │   │ S1 · 来自原始数据       │
│▌拒绝作答的记录视为缺失          [! 有发现] - - - - - │ - │ 拒答被记成了数值        │
│                                                     │   │ 已修 · AI 错了 · 无所谓  │
│┃┌─ 决策点 · 固定效应设定 ─────────────────────────┐ │   └──────────────────────┘
│┃│ ● 职业固定效应（已选）              当前结论     │ - │ ┌──────────────────────┐
│┃│ ○ 职业大类固定效应           换成它：结论不变    │   │ 质疑                   │
│┃│ ○ 不加                       换成它：结论变弱    │   │ 拒答是否集中在某一类简历上？│
│┃└───────────────────────────────────────────────┘ │   │ 转成问题 · 忽略          │
│ ┌ ─ 关键结果已遮住 ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┐  │   └──────────────────────┘
│   先写下你预期的方向和大小   [你的预期…]  [揭晓]    │
│ └ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┘  │
└─────────────────────────────────────────────────────┘
```

只有决策块用强调色：它是这一段里人真正要做的事。已核对的数字只占一个小标记，发现和质疑放在页边。

### 一次审核的节奏

1. **定向**（约 1 分钟）：地图、一句话结论、"没查什么"。只读。
2. **上游裁决**：framing、设计、操作化的决策点，从上游往下。
3. **下游抽查**：来源标记抽查确认；处理 S1 和 S2 发现。
4. **签收**：看未回应项和 AI 默认项，签收或再来一轮。

上游先于下游，因为上游一改，下游的确认就失效。

### 脚手架逐步撤掉

- 某类 V 检查连续多次确认都没改动，以后不再请人抽查，只在签收清单列出。
- 某类型上的预测一直很准，预测闸门减少。
- 规则已升级为自动检查，对应提问不再出现。

撤掉的东西随时可恢复。

## 人的介入与反馈

| 时刻 | 人做什么 | 典型用时 |
| --- | --- | --- |
| 计划确认 | 调整档位、增删环节、指定"这次特别要查什么" | 1–2 分钟 |
| 决策点裁决 | 对 J 类做选择，处理 S1/S2，回答预测 | 主要时间 |
| 最终签收 | 看验证清单和未解决项，决定交付或再来一轮 | 1–2 分钟 |

- **锚定在对象上**：每条反馈挂在决策点或发现上。
- **选择优先于书写**。
- **固定的反应类别**：已修 / AI 错了 / 是故意的 / 无所谓 / 这是一类问题。
- **一次纠正一类**：标为"一类问题"后，AI 找出所有同类实例供批量确认。
- **允许语音**：口述由 AI 转写并挂到节点上。

反馈写入 `feedback.jsonl` 后，调用 `review-apply` 修改产出并触发差异再审。

## 长期沉淀

一条反馈有四个去处，越往下越省人力。同类反馈重复出现，`review-learn` 提议往下升一级，人批准后生效。

1. **一次性修正**
2. **规则**：写进 `rules.md`
3. **自动检查**：有真值可对照的规则写成 `checks/` 脚本
4. **生成时的默认**：写进 `review-aware` 或项目 `CLAUDE.md`

- **区分正确性和偏好**：正确性可升到自动检查；偏好只停在规则层。
- **记录命中率**：长期不触发或总被驳回的规则提议归档。
- **逃逸回流**："漏掉了"按钮把事后发现的问题记入 `incidents.jsonl`，标明环节和本该在哪一步被抓住，变成回放评测集的一条。
- **改了就回放**：规则、提示或模型一变，在评测集上重跑。

## 自我实验与度量

| 度量 | 回答的问题 | 怎么得到 |
| --- | --- | --- |
| 人工用时 | 审核花了多少分钟 | 界面自动计时 |
| AI 工作量 | AI 跑了几轮、启动了几个审核者、用了多久 | 会话日志里的轮次和起止时间 |
| 审核精确率 | AI 的发现有多少被确认 | 反应类别 |
| 逃逸率 | 事后又发现多少问题，按严重度 | `incidents.jsonl` |
| 预测准确度 | 心智模型准不准，是否随时间下降 | 先预测后揭晓的记录 |
| 注意力错配 | 时间花在哪些环节，问题出在哪些环节 | 停留时间对比发现分布 |
| 反馈量趋势 | 同类任务需要的反馈是否减少 | 每次的反馈条数 |
| 质量评分 | 对交付物的打分，当时一次、一周后一次 | 签收时和回访时 |

可做 n-of-1 随机化：每份产出随机分到"完整流程"或"平时的方式"，积累二三十份后比较。埋错校准默认关闭。回放实验可回答"模型能力够不够"：把事故还原到发生时的状态，分别只给产出、给产出加真值、再加环节定义，看在哪一档能抓到。

## 技术选型与跨 agent 兼容

- **Skill 格式**：`SKILL.md` + 脚本的目录结构，Claude Code 可直接加载。其他 agent 的支持情况开发时逐个确认；不支持的，提供等价的命令或提示文件作为适配层。
- **文件格式**：`plan.json`、`map.json` 用 JSON Schema 定义并在写入时校验；发现、反馈、事故用 JSONL。Schema 是最重要的约定，要最先定。
- **审核界面**：本地网页，小型 Python 服务读取会话文件并提供页面，前端单页应用。agent 写完文件界面自动刷新；界面操作写回文件，agent 下一轮读取。
- **并行审核者**：支持子 agent 的环境并行；不支持的退化为顺序执行。
- **分享**：需要时把某次会话导出为只读静态页面。默认不导出。

## 开发路线

先用一个类型（科研报告）跑通全流程，再扩展。测试方式是用户在实际工作中直接使用：把正在进行的科研报告或研究计划交给系统审核，边用边记录哪里有帮助、哪里打扰了人。

| 阶段 | 内容 | 完成标准 |
| --- | --- | --- |
| 0. 约定 | 文件 schema、科研报告的 `TYPE.md`、各 skill 的文字版 | 在一份真实产出上手动走通，文件格式不再改 |
| 1. 自审 | `review-start` 和 `review-run`，不做界面，结果写成 markdown | 在一份真实产出上跑通；用户认为至少一条发现有价值，误报不超过发现总数的一半 |
| 2. 界面 | 全局地图、决策点卡片、发现队列、反馈写回、`review-apply` | 用户完成一次完整审核，体验比纯文本好 |
| 3. 沉淀 | `review-learn`、事故记录、回放评测、`review-stats` | 连续用两周，至少一条规则从反馈升级而来 |
| 4. 扩展 | 其余三个类型、预测与揭晓、敏感度分析、跨 agent 适配 | 每个类型至少审过两份真实产出 |
