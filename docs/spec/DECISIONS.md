# 设计决定记录

格式：日期 · 决定 · 理由 · 考虑过的其他做法。

## 2026-10-21 · 工作区放在仓库外的单独目录

- **决定**：工作区（类型规则、sessions、ledger）放在仓库外，默认 `~/review-workspace`。仓库只放 skill、schema 和默认类型模板。所有文件中的路径都相对于会话文件夹或工作区根目录。
- **理由**：用户 的选择。审核记录和代码分开，换仓库或重装不受影响。
- **其他做法**：仓库内加 `.gitignore`（开发方便但记录和代码绑在一起）；可配置路径（第一版多一层配置）。

## 2026-10-21 · schema v0.1 的几个约定

- **id 用会话内的短编号**（`D01`、`F001`、`FB0001`），全局唯一靠 `(session_id, id)`。理由：你会在对话里直接说"F003 是误报"，短 id 读写成本最低。事故跨会话，用 `I-<日期>-<序号>`。其他做法：ULID/UUID，唯一但难读。
- **findings.jsonl 和 feedback.jsonl 只追加**。发现状态变化时写一行同 id、`rev` 加一的完整快照，最后一行生效。理由：历史可回放，界面和 agent 不用改写同一行，减少写冲突。其他做法：原地改 JSON 文件（简单，但丢历史、易冲突）。
- **只有通过验证的发现写入 findings.jsonl**；被丢弃的候选只在 metrics.json 里计数。理由：落实"没有证据的发现不发"，文件里每条都是能给人看的。其他做法：候选和已验证的混在一个文件里用状态区分（方便调试审核者，但界面要过滤，容易漏）。
- **"人的反应"和"AI 一侧状态"分开**：反应类别只在 feedback.jsonl；findings 的 `status` 只记 AI 做了什么（修了、关了、被合并）。理由：一个事实只在一个地方。
- **承重分数用 0–3 整数**，并标明依据（真跑过敏感度 / 依赖关系 / AI 估计）。理由：人一眼能读懂；区分算出来的和猜出来的。其他做法：0–1 连续值（显得精确，实际上没有这个精度）。
- **主张来源类型加了 `unsourced`**：设计里要求没有来源的主张单独列出。
- **反馈多了 `confirm`、`prediction`、`plan_confirm` 三种**：设计里的一键抽查、预测闸门和计划确认需要落成记录，固定的五种反应类别不变。
- **签收写在 feedback.jsonl**（`kind: signoff`），绑定 `artifact_hash`。理由：签收也是一次人的动作，和其他反馈放在一起计时、计数。

## 2026-10-22 · 用户 睡前授权连续推进

- **决定**：用户 说"一直往下做，直到遇到真正的阻碍"。因此没有在 schema 审阅这个关口停下，而是继续完成 Phase 0 的 2、3 步，并实现 Phase 1 的脚本，在仓库自带的合成产出上跑通。所有工作在 `overnight-phase0-1` 分支上，按提交顺序可以逐步审阅。没有开始 Phase 2（界面），没有碰 用户 的其他项目，没有建 `~/review-workspace`。
- **理由**：她明确授权；schema 若在审阅后要改，代价是改一个脚本和几个示例，不大。
- **仍然需要她决定的**：schema 审阅；Phase 0 第 4 步挑一份真实产出；Phase 1 的完成标准必须在她的真实产出上判断。

## 2026-10-22 · 确定性的部分交给脚本 `scripts/rh.py`

- **决定**：建会话、哈希、编号、校验、追加写入、度量、摘要渲染都由一个 Python 脚本完成；skill 只做需要判断的部分。依赖（jsonschema、pyyaml）写在脚本头部，用 `uv run` 自动准备，不装进系统 Python。
- **理由**：这些步骤必须精确，交给模型做会有编号冲突、漏校验、格式漂移。脚本也是"写入时校验"的落点。
- **其他做法**：每个 skill 各带脚本（重复）；纯靠模型按说明写文件（不可靠）。

## 2026-10-22 · 写入发现时机械核对证据和锚点

- **决定**：`RH add-finding` 拒绝写入锚点原文在快照里找不到、或 `file` 证据摘录在文件里找不到（或行号偏离超过 2 行）的发现。
- **理由**：试跑中，查找者在证据里写了"示意性"命令，被验证者发现。机械核对再加一道闸，让"没有证据的发现不发"不只依赖模型自觉。命令类证据无法机械核对，仍靠验证者重跑。

## 2026-10-22 · 加 `caused_by`，摘要按根源折叠

- **决定**：发现可以标明根源发现；摘要把连带问题折叠在根源下面，第一行写"按根源合并为 N 个问题"。
- **理由**：试跑中一个解析错误引出三条发现，分开列出读起来像三个问题，浪费注意力。
- **其他做法**：把连带问题合并成一条（丢失具体位置和各自的改法）。

## 2026-10-22 · 摘要里预测问题放在所有结果之前

- **理由**：放在后面时人已经看到了结果，预测就没有意义。Phase 1 没有界面，只能靠位置做"遮住"。

## 2026-10-22 · 每轮存档上一轮的 map.json

- **决定**：`round-start` 把上一轮 `map.json` 存到 `work/round-N/`；校验时只对当前版本的发现和反馈检查 id 引用。
- **理由**：试跑第 2 轮时，改写后的 map 删掉了旧主张，旧发现的引用全部失效。

## 2026-10-22 · 用冷启动 agent 测 skill 文本

- **决定**：skill 文本的好坏用一个没有任何上下文、只读 `SKILL.md` 的 agent 来测，而不是由写 skill 的人自己执行。
- **理由**：自己执行时会不自觉地用上下文补全缺口。冷启动一次就找出 18 处文本问题。以后 skill 文本有较大改动时，都重跑一次冷启动测试。

## 2026-10-22 · 计划草稿由脚本生成

- **决定**：新增 `RH init-plan`，按 TYPE.md 和档位生成带 `TODO` 占位的 `plan.json`；`RH validate` 在 `TODO` 未填完时报错。
- **理由**：冷启动 agent 只能从 schema 手工拼计划骨架，容易漏字段。

## 2026-10-22 · 前提写成主张，不写成决策点

- **决定**：没有备选、只能成立或不成立的前提（如"配对简历除姓名外完全相同"）写成主张；材料不在项目里时标 `unsourced`，由用户在摘要里一键确认。
- **理由**：硬把前提写成决策点，需要凑一个不真实的备选项。
- **其他做法**：在 map.json 里加一类"前提"对象（更清楚，但多一种结构；先看真实使用中前提多不多）。

## 2026-10-22 · 主张只有经验证者确认才算 verified

- **理由**：冷启动试跑指出，查找者自称"核对过没问题"的主张如果直接标 verified，就绕过了独立验证。

## 2026-10-22 · 预测问题不能透露核查结果

- **决定**：预测型决策点只问用户对研究问题本身的预期，只有一个选项（产出原文的结果）。
- **理由**：第二次冷启动试跑时，预测问题写成了"去掉拒答后你预期……"，在用户读到发现之前就泄露了主要发现，预测就失去了检验心智模型的作用。

## 2026-10-22 · origin 的边界

- **决定**：`introduced` 包括同一工作里写的代码和分析；`source_material` 只指工作之外的数据或材料本身有错；`inherited` 由上游决策（`origin_decision`）或另一条发现（`caused_by`）引起。
- **理由**：两次冷启动对"解析代码的 bug 算哪一类"给出了不同答案。

## 2026-10-22 · 进入 Phase 2（界面）

- **决定**：用户 批准进入 Phase 2。Phase 1 的完成标准（在她的真实产出上跑通）还没验证，留到 Phase 2 的验收一起做：第一次完整审核就用一份真实产出。
- **理由**：她认为界面才是日常使用的主要入口，先有界面再在真实产出上试，能一次检验两个阶段。

## 2026-10-22 · 界面只在本机访问

- **决定**：界面服务只监听 `127.0.0.1`，在装了 skill 的那台机器上用。不做远程访问和登录。（交接文档待决问题 4）
- **理由**：用户 的回答："just where the skills are installed"。
- **其他做法**：SSH 端口转发、局域网加访问令牌、Tailscale。以后需要时，SSH 转发不用改代码。

## 2026-10-22 · 界面的技术选型

- **决定**：服务用 Python 标准库（`http.server`），通过 `uv run` 运行，复用 `rh.py` 的校验和写入函数。前端是单页应用，用 Preact + htm 的独立构建版（一个文件），直接放进仓库的 `ui/vendor/`，不用 npm，不需要构建步骤。页面每隔一会儿查一次会话文件是否有变化，有变化就自动刷新。
- **理由**：机器上没有 node。界面由 agent 启动（`review-open`），越少依赖越不容易出错。放进仓库的库文件保证运行时不联网。Preact 提供组件，文档审核层、决策块、页边注这类交互用组件写不会乱。轮询比服务器推送更简单，几秒的延迟可以接受。
- **其他做法**：Vite + React + TypeScript（需要 node 和构建步骤）；纯原生 JS（交互一多就难维护）。
- **安全**：只监听本机；检查 `Host` 头防 DNS 重绑定；写入请求检查 `Origin`；能读的文件只限会话文件夹和计划里登记的真值位置。

## 2026-10-22 · 预测前遮住哪些内容，由类型声明

- **决定**：`TYPE.md` 的前置信息加 `prediction_mask`（科研报告是 interpretation、visualization、conclusion）。有未完成的预测时，界面遮住预测锚点所在的段落，以及这些环节的主张所在的段落；顶栏和地图上的发现计数也先不显示。
- **理由**：最初只遮预测锚点所在的段落，试看时发现"结果"一节的数字仍然露在外面，预测就没有意义了。哪些环节算"结果"因类型而异，所以由类型声明。
- **其他做法**：遮住所有 `computed` 主张（会把"60 对简历、8 个职业"这类做预测需要的背景也遮掉）；在 map.json 里给每个预测型决策点列出要遮的主张（要改 schema，先不做）。
- **注意**：工作区里的类型是 `review-setup` 时复制过去的，已有的工作区要手动更新 `TYPE.md`（或重新运行 `RH init`，它不会覆盖已有文件，所以需要先删掉旧的 TYPE.md）。

## 2026-10-22 · review-apply 的确定性部分交给脚本

- **决定**：新增 `RH apply-plan [--write]`：按最新反馈整理修改清单（要改、改选、回答、标为有问题、下游失效、用户自己改、关闭、没回应的 S3），有未回应的 S1 时拒绝（退出码 4）。`--write` 关闭不改的发现，并更新决策点状态（改选的 `changed`，其下游递归标 `invalidated`，确认过的 `confirmed`）。修改产出本身由 agent 在 `work/apply-<轮次>/` 的副本上做，经用户同意才写回原文件。
- **理由**：反馈取最新一条、下游递归失效这些规则必须一致，写在脚本里不会因 agent 理解不同而变。

## 2026-10-22 · 界面暂不做语音输入

- **理由**：浏览器自带的语音识别（Chrome 的 Web Speech API）会把音频送到外部服务，违反"本地优先"。以后如果要做，用本机的转写（例如 macOS 听写，或本地 whisper），由 agent 转写后写成 `source: voice` 的反馈。

## 2026-10-22 · 科研报告按七个方面组织审核

- **决定**：科研报告类型（`types/research-report/TYPE.md`）的审核主线改成 用户 自己审学术报告用的七个方面：核心问题、研究定位、方法是否对题、实现与测量、结果呈现、给读者的解读、整体框架。原来的检查项不删，归到对应方面下面；补四个原来缺的判断类检查项：`positioning`（与已有研究的关系）、`presentation`（重点是否讲清楚）、`reader_reading`（读者会不会读歪）、`coherence`（各部分是否连成整体）。检查项名称改成白话。`TYPE.md` 新增 `aspects`，每个环节加 `aspect`；`init-plan` 把它们复制进 `plan.json`（schema 新增可选的 `aspects` 和 `stages[].aspect`）。摘要开头加一张按方面的表，界面地图按方面分组，卡片上写"方面 · 检查项"。
- **理由**：她在一次真实审核里（Claude 审 opencode 写的报告）用这七个方面重审，发现原来的类型偏重"有没有算错"，对"重不重要、讲没讲清楚、是不是一个整体"几乎不查。结果呈现、读者解读、整体框架上的问题按影响定 S1/S2，不再当作只列不修的 S3 表述问题。她也觉得界面和汇报里术语太多。
- **范围**：七个方面只用于学术报告。她说实验设计、分析写作的审核方面不同，以后各自的类型各写各的 `aspects`。
- **其他做法**：用七个方面直接替换原来的环节（会丢掉"实现与测量"下面细分的核实步骤，而那是自审最有把握的部分）。

## 2026-10-23 · AI 先自审自改，再交给人

- **决定**：审核流程改成：AI 读产出 → 设计审核方面（每个方面管哪些内容、关键标准是什么）→ 自审 → **在副本上自己改** → 再审，最多 3 轮，或者没有 S1/S2 就停 → 剩下的问题和改动对比交给人，在页面上处理和讨论 → 人同意后才写回原文件。AI 自改时什么都可以改，包括靠判断的部分（定位、框架、措辞），但要逐条记下改了什么、为什么。
- **理由**：用户："既然是 AI 第一个版本，只是自己要多审核，那么它当然什么都可以改"。人的注意力留给 AI 自己解决不了的问题。
- **不变的规则**：原文件只有在人同意后才写回；AI 的改动都留记录，人能看到每一处改了什么。
- **取代**：原设计里"每轮之间先由人回应，AI 再改"。人回应之后的修改（review-apply）仍然保留，用于人给出新意见之后。

## 2026-10-23 · 审核方面的情境库

- **决定**：为不同情境预设审核方面，作为 AI 设计审核方面时的参考例子：学术报告（已有）、实验设计与研究计划、数据分析写作、产品方案、一般文章。AI 起草，用户 修改。遇到新情况，AI 参照这些例子为这份产出提出审核方面，写进计划，由人确认。
- **理由**：她说"we need predefined dimensions in different situations — at least as few shots"。

## 2026-10-23 · 页面上的讨论和长期建议

- **决定**：页面上可以针对某个问题或整份产出和 AI 讨论，也可以写对审核本身的长期建议。页面不调用模型：人的话写进会话文件，由开着的 agent 对话回复。长期建议交给 review-learn。
- **理由**：她要求剩下的问题能在页面上和 AI 讨论，并且页面上能留下有助于长期审核质量的建议。

## 2026-10-23 · 真实的研究项目只作为测试材料

- **决定**：这个项目是正在进行的正式工作，只把它的报告复制进工作区做测试，任何时候都不写回、不修改原项目。新流程做好之后再在它上面试。

## 2026-10-23 · 要你关注的区域直接在正文里标出来

- **决定**：正文里每个要人处理的地方（要裁决的决策点、交给人的严重问题、需要确认的前提、正在讨论的条目）成为一个"关注区域"：它覆盖的段落加底色和左边框，区域开头写出要回答的问题和"去处理"。开头有一行汇总（几处、各是什么），可以切换"只看这些区域"，其余段落变淡。右侧细条也标出这些区域。
- **理由**：用户 希望"需要讨论或者重点关注的问题区域，也有一些对应的可视化（高亮一定区域，指出来一些要回答的问题）"。原来的标记是点状的（某句话下划线），看不出一片区域、也看不到问题本身，要点开卡片才知道。
- **AI 改不了的问题**：用 `RH handoff` 写明原因交给人，自改循环不再算它，区域里直接显示原因。

## 2026-10-27 · AI 做专家判断，不做计算

- **起因**：第一次真实审核（一个真实的研究项目）时，AI 把 1.5 GB 运行日志复制进会话，几个审核子 agent 同时重跑分析脚本，把 16 GB 的电脑内存用光；补上排队和内存检查后，又跑满了一次。用户："what you do is not to recalculate, but from a specialist view to know if this way of analysis is reasonable, robustness or not. you do the brain work, not calculation work."
- **决定**：
  - 审核对象是产出本身。AI 像这个领域的资深审稿人一样，按审核方面判断：问题对不对、方法能不能回答它、分析选择是否合理、换一种合理做法结论大概会不会变（推理并说理由）、解读有没有超出证据、缺了什么。
  - **不运行、不重算**：不运行项目代码，不读入原始数据或日志。可以读设计文档、代码、已保存的结果来理解作者做了什么。要重算才能回答的疑问，作为问题交给用户。
  - 数字只抽查主结论依赖的几个，对照已保存的结果文件。
  - 每个审核方面多两样东西：`expert_questions`（资深审稿人会问的问题）和 `red_flags`（常见毛病）。审核者按方面分组，每组相当于这些方面的行家。
  - 审核的产出多了每个方面的评价（`map.json` 的 `assessments`：扎实 / 基本可以 / 有明显问题，一句话、理由、值得想的问题），摘要和页面上先给评价，再列具体问题。
  - AI 自改不产生新数字；需要重算或改代码才能修的，先把文字改到证据能支持的程度，再交给用户。
- **情境库**：学术报告（七个方面）、实验设计与研究计划、数据分析写作、产品想法与方案、博客与评论文章（取代"一般文章"）、课程设计（新）、技术设计（新）。都按"资深审稿人"的视角重写，除学术报告的七个方面外仍是待 用户 修改的草稿。
- **撤销**：同一天加的资源检查和重跑排队（`rh resources`、`rh heavy`）已经撤掉，不重跑就不需要它们。

## 2026-10-27 · 深入、侦探式、连贯；线索用问题和高亮交给人

- **起因**：用户 读了 Freedman（1991）"Statistical Models and Shoe Leather"："I focus on finishing the work and not think deeply. same as you." 第一次真实审核主要在查"说法和结果是否一致"，没有问"结论是否真的被确立"。她的要求："deeply into analysis, detective, coherent - this is very important"；反常和疑点"use questions and highlight as your tool to guide the user"。
- **决定**：
  - 学术报告加第八个方面"证据是否立得住"（环节"侦探式检验"）：设计本身说明问题还是靠模型撑着、主结论的推论检验了没有、每个反常怎么解释、对立解释排除了没有、最朴素的比较是什么样、有没有回到原始材料。研究计划和数据分析写作的相应方面加了同样的专家问题。
  - 新的对象**线索**（`map.json` 的 `leads`，L01…）：反常的结果、没检验的推论、没排除的另一种解释、模型代替了设计、前后接不上。每条写看到了什么、为什么要紧、问用户的问题。AI 不修线索，也不替用户回答；页面上把相关段落用单独的颜色高亮，问题写在上面，用户回答或讨论。只有确定是错的才作为发现由 AI 修。
  - 查找者写线索，验证者核实、合并、按威胁排序（最多 8 条）。

## 2026-10-27 · 写法、两层结构与笔记类型

- **起因**：用户 读页面上的审阅意见："根本看不懂啊……什么叫薄性别层？""put your 事实 and 判断, instead of murmuring about 你不做什么，用户要做什么"；"this review report only adds burden for me"。原因是技能文本本身用内部简写，子 agent 模仿了这种文风，主 agent 又没有编辑就交给了她。
- **决定**：
  - `skills/WRITING.md`：先写事实，再写判断；学术写作的正常语言；不出现工具内部的说法，不写分工；附本次审阅中的改写对比。所有子 agent 必须先读；主 agent 在交给用户之前逐条编辑。
  - **两层**：概览（研究叙事、测量、分析、结果与解读、关键问题）写全文的架构；正文批注只处理细节。
  - **笔记类型**：✎ 修改、💡 建议、？ 值得追问、⚠ 待核实、💬 讨论中，全页面同一套颜色与图标；严重程度作为文字附在标签上。
  - **分流**：能改的由 AI 改（包括摘要、标题与结果不一致）；交给作者的只有需要判断的研究决策与需要核实的事实；技术细节只以它对结论的影响出现。
  - 学术报告按 用户 的层次重组为六层：研究问题与定位、文献基础、研究设计、结果、分析、解读。

## 2026-10-27 · 审阅过程、退回作者、持续改进与答辩模式

- **审阅过程**：页面的"审阅过程"一页讲述 AI 作为审稿人做了什么：每一轮提出与保留的意见、按层次归类的修改、下一轮确认解决的问题、留给作者的问题，以及核查记录。由已有记录重建，不另外记录。
- **退回作者**：AI 审稿人先判断稿件是否值得用户花时间（`readiness`）。决定主要结论能否成立、又不需要用户判断的问题，先退回作者（往往是另一个 agent）：写出 `handback.md`（依据指向原项目），发现作者的会话正在运行时，问用户一句后发送。用户 选择"写出清单，作者在运行就发送"。
- **持续改进**：用户的回应就是对审阅的评价——不成立（误报）、无关紧要（价值低）、撤销的修改（修改过度）、"AI 遗漏的问题"（最重要的信号，页面上新增入口）、建议、对线索的回应。`RH signals` 汇总全部审阅，`review-learn` 据此提出对框架、规则、写法的具体修改，用户逐条同意后写入，并记录在 `ledger/learning-log.jsonl`。
- **答辩模式**（`review-devil`）：独立的功能。AI 按作品类型扮演最严格的内行提问者，只问 5–7 个答不好就会改变判断的问题，一次一个，按回答追问，最后逐题评价并保存记录。用户 选择在对话中进行。

## 2026-10-27 · 审阅结束时，AI 主动回顾这次审阅

- **起因**：用户："AI should proactively make the summarize as the last step, we should guide user to do that."
- **决定**：回顾不等用户要求。用户在页面上点"定稿"或"再审一轮"时，页面同时通知对话；AI 先完成写回或修改，然后主动回顾这次审阅（`RH signals --session`），提出至多五条改进今后同类审阅的建议，请用户逐条确认。用户在这次审阅中回应很少时，先问两个简短的问题（哪些意见有用、哪些多余；有没有遗漏），把回答记下再提议。页面的"完成审阅"一页事先说明这一步。

## 2026-10-27 · 页面上的正常使用就是改进审阅的依据

- **起因**：用户："the user's reaction on the frontpage can also become something that can be saved? so that we don't need user to do another thing, but their data on the frontpage itself is the source to iterate"
- **决定**：用户在页面上的回应本来就逐条保存（同意、不成立、无关紧要、撤销修改、对线索的想法、改选的决策、遗漏的问题）。再补两类不需要用户额外操作的依据：
  - **讨论**：用户就某条批注与 AI 讨论，往往说明它不清楚或有争议；
  - **阅读记录**（`activity.jsonl`）：打开了哪些批注、看了多久、从概览点了哪些引用。从未打开的批注可能是噪声；看了很久却没有回应的，可能写得不清楚。只保存在本地的审阅文件夹中，只用于改进审阅，不触发页面刷新。
  - `RH signals` 汇总这些，`review-learn` 据此提议。

## 2026-10-27 · 用户与作品的关系、修改的范围（来自第一次测试审阅）

- **起因**：Dropbox 申请的测试审阅中，主持审阅的 agent 指出几处流程问题：替作者在第一人称申请里新增句子，结果两处都改错了；评判别人已完成的作品时，"请你选择"没有意义；AI 改错的地方只算表述问题，循环照样交给用户；同一短语出现两次时，修改记录的核对会对错位置。
- **决定**：
  - 计划新增 `user_role`：`author`（用户自己的作品或 AI 替用户写的初稿，AI 修改副本，选择留给用户）与 `evaluator`（评判别人已完成的作品，AI 不改写原文，可选做法写成向作者的提问，结论是审稿人的结论）。
  - 计划新增 `revision_policy`：`full` 与 `narrow`。作者本人口吻的文本（申请文书、个人陈述、随笔、小说、第一人称的路演材料）用 `narrow`：只删减、收窄、按材料更正，不替作者新增论断。个人陈述、创意写作、博客的类型默认为 `narrow`。
  - 第 2 轮及以后提出的问题（都针对 AI 自己的修改）不论严重程度，都由 AI 修正后才交给用户。
  - 修改记录按上下文定位，同一短语出现多次时不再对错位置。
  - 体裁本身不要求的层次，在计划中排除并写明理由。

## 2026-10-27 · 创意写作以立意为先；会议纪要按标准结构与录音核对；技术设计只看三件事

- **创意写作**：用户 审阅《末班车》时写道："一个写作，最重要的，最关键的就是核心的立意……最好的维度就是核心的思想是不是有深度，用户本身说的想要表达的是什么，是否表达出来，文风是否合适，文字是否有节奏。"原框架是六个技巧层面的维度，连同我事先埋下的缺陷（铺垫过长、直接说情绪、结尾说教）都停留在技巧层面，看不到最根本的问题：没有立意。重组为四层：立意、意图的实现、文风、语言的节奏；人物、场景、结构、对话作为手段，只按是否服务立意判断。审阅前先问作者想表达什么（计划的 `intent`）。AI 不修改作品（`revision_policy: none`），只提问与建议。
- **会议纪要**：用户 的标准是最上方要点摘要，其次是待办事项表（负责人、所做的工作、截止时间），再是讨论；有录音或逐字稿时以它为准核对。加入框架。
- **技术设计**：用户："only need to focus on if the technical plan can fulfill the target, and if there is risky points (complex calculation, 边界情况, cost-needed parts, large-volume data processing) and double check those point, and decide whether the current plan do good on performance (resource usage, memory, cpu, and time's balance)"。重组为三层：目标与方案、风险点（审阅者对每个风险点自己推理复核）、性能与资源。接口命名、文档格式等不在范围内。

## 2026-10-27 · 课程设计与产品想法审的是设计本身，不是文档

用户指出：这两类作品通常是自己写的方案（与 AI 讨论后整理出的产品想法、自己设计的一门课），不是正式的大纲或需求文档。审阅要回答的是设计好不好，而不是格式与措辞。

- **课程设计**改为七个方面：课程要达到什么、课程划分与时间排布、课程环节、学生的兴趣、内容的表达（如何讲懂）、内容的真实与可靠、还需要设计的部分。去掉建构性对齐、包容性等以正式大纲为标准的方面（考核只问是否测到课程的重心）。
- **产品想法**改为六个方面：核心点、第一性原理（最根本、最没把握的假设）、经得住推敲吗、核心挑战、现有的类似产品、最短路径。去掉市场规模、成功指标体系、上线计划等以正式需求文档为标准的方面。

## 2026-10-28 · 方案按方案来审（来自课程与产品的测试审阅）

两次测试审阅暴露的五个问题，原因相同：审阅流程默认对象是一份完成了的研究报告。

1. **评级尺度。** 类型的 `TYPE.md` 写 `work: plan`（目前是课程设计与产品想法）时，方面评价改用"想清楚了 / 有方向，未想透 / 尚未涉及"（clear / partial / open），不再用"扎实 / 基本成立 / 存在明显问题"。一晚上的想法六项全是"存在明显问题"，读起来是苛责，也没有信息。
2. **建议的路径。** 方案类的概览加 `overview.path`：先做什么、砍掉什么、用什么最便宜的办法检验最没把握的一点，按先后列 3–6 步。这类建议只写在这里，批注只写那一处怎么改。校验要求方案类必须有路径，非方案类不能有。
3. **每件事只出现一次。** 关键问题、批注、线索、决策点、路径、任务之间，同一件事选最合适的位置写一次，其余用 refs 指过去。方案类的决策点只记尚未定下、又影响其余部分的选择，不再同时写成发现。
4. **作者自己的方案。** `work: plan` 且 `user_role: author` 时，结论写"可以着手实施 / 动手之前，先想清楚这几件事"，不列退回任务（下一步就是建议的路径），不写 handback。页面上"研究决策"改称"需要你作的选择"。
5. **线索的种类按类型。** `TYPE.md` 的 `lead_kinds` 决定可用的种类；方案默认是未经检验的假设、尚未作出的选择、尚未考虑的部分、前后不一致。研究类的五种不变（"论证不连贯"改称"前后不一致"，两类通用）。

另：课程方案中"时间加起来超出"这类矛盾，原文无法判定删哪一部分，写成建议并给出几种排法，不由 AI 直接改（与"原文没有依据时不替作者选择"一致）。
